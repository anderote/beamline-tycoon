# Windows Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Six placeable window types with glass-tint variants that punch real
openings in walls, glow warm at night, and give the rooms they light a morale
contribution.

**Architecture:** Windows are a sibling of doors, deliberately *not* an
extension of them — they get their own catalogue, their own occupancy map and
their own save field, because `doorOccupied` is read as "this edge is
passable" by room detection. Rendering shares the door pass's wall-surround
logic (extracted to one method) and adds a frame + glass pane. The night glow
rides the darkness ramp the lighting work already established. Daylight rides
the room-morale map that zone furnishings already populate.

**Tech Stack:** Vanilla ES modules, Three.js (THREE is a CDN global — never
import it in renderer files), Vite, node test runner (`npm test` →
`scripts/run-tests.mjs` over `test/*.js`), Playwright for browser tests.

**Spec:** `docs/superpowers/specs/2026-08-13-windows-design.md`

## Global Constraints

- **Pre-release, single-user: ignore save compatibility.** Old saves may
  break. No migrators, no version bumps, no graceful-degradation shims.
- **Do not commit.** Leave your changes in the working tree; the user decides
  commit boundaries. Never `git add`, never a bare commit, never `git commit -a`,
  never stash — multiple sessions share this checkout and the index is shared
  state. Report the files you changed instead.
- **Don't start or kill a dev server.** The user keeps one running.
- **No new art.** Frames reuse `metal_brushed` / `drywall_painted` /
  `metal_dark` from `MATERIALS`; glass is a coloured transparent material;
  palette previews fall back to the existing colour-swatch path. Do not
  generate PNGs.
- Windows must never appear in `doorOccupied`, and nothing that answers
  "can something pass through this edge" may consult `windowOccupied`.
- Doors must look **exactly** as they do today after the render refactor.
- New tests are `test/*.js`, run by `node test/<file>.js`, failure signalled
  by a non-zero exit code. Match the style of the neighbouring file you are
  extending.

### Task 2: Window state, placement and save

The sim half. Depends on Task 1.

**Files:**
- Modify: `src/game/Game.js` — state init (`:280` neighbourhood, beside
  `doors`/`doorOccupied`), `SAVE_KEYS` (`:55`), the door placement block
  (`:1352`–`:1428`) as the model, scenario apply (`:4196`/`:4234`) and load
  rebuild (`:4767`)
- Test: `test/test-windows.js` (extend)

**Interfaces:**
- `state.windows` — `[{ type, col, row, edge, variant }]`
- `state.windowOccupied` — `"col,row,edge" -> windowType`
- `placeWindow(col, row, edge, windowType, variant = 0) -> boolean`
- `placeWindowPath(path, windowType, variant = 0)`
- `removeWindow(col, row, edge)`
- Emits `windowsChanged`
- `SAVE_KEYS` gains `'windows'`

**Rules to encode:**
- Placement requires `state.wallOccupied[key]` (under either edge alias) and
  requires the wall to satisfy `wallHeight >= sillHeight + openingHeight + 1`.
  Failing either is a no-op: no state change, no funding charged, return
  false. `placeWindowPath` skips such edges and still commits the rest.
- Placing a window on an edge holding a door removes the door (and emits
  `doorsChanged`); `placeDoor` gains the mirror-image removal of a window
  there. Exactly one opening per edge, always.
- Re-placing the same type+variant on the same edge is a no-op (match how
  `placeDoor` short-circuits); a different type replaces in place.
- `_detectRoom` is **not** touched. Add a comment at its `edgeBlocked` helper
  recording that windows are deliberately absent.
- Load and scenario apply rebuild `windowOccupied` from `windows`, in the same
  two places `doorOccupied` is rebuilt.

- [ ] **Step 1: Write the failing tests**

Extend `test/test-windows.js`: place/remove round-trip; the fit rule (succeeds
on `officeWall`, no-ops on `cubicleWall`, funding unchanged in the second
case); door/window mutual exclusion in both directions; `windowOccupied`
rebuilt after a serialize/deserialize round-trip; and — the load-bearing one
— two tiles separated by a walled edge stay in different `_detectRoom`
results when a window is on that edge, while a door on the same edge merges
them.

- [ ] **Step 2: Implement**
- [ ] **Step 3: Verify** — `node test/test-windows.js`, then `npm test`
- [ ] **Step 4: Report** — list changed files; leave them uncommitted

### Task 3: Daylight feeds room morale

Depends on Task 2. Independent of Tasks 4 and 5 — can run alongside them.

**Files:**
- Modify: `src/game/Game.js` — `computeRoomMorale()` (`:3518`)
- Test: `test/test-windows.js` (extend)

**Interfaces:**
- `computeRoomMorale()` keeps its signature and return shape (`Map` of
  room key → morale). Windows add to the same map.
- Export `DAYLIGHT_ROOM_CAP = 3.0` from `Game.js` so the test reads the real
  constant.

**Algorithm:** after the furnishing loop, walk `state.windows`. For each, take
the two tiles either side of its edge. For each side, resolve the room via the
same `tileToRoom` / `_detectRoom` memoisation the furnishing loop uses — reuse
it rather than adding a second cache. Skip a side whose flood fill reached the
500-tile cap (outdoors). Accumulate that window's `daylight` into a per-room
daylight subtotal, keyed the same way (`[...room].sort()[0]`). After the walk,
add `min(subtotal, DAYLIGHT_ROOM_CAP)` into the returned morale map.

The cap applies to the daylight subtotal only — furnishing morale is added
uncapped, as today.

- [ ] **Step 1: Write the failing tests**

A room with two `officeWindow`s gains `0.8`; the same room with ten
`pictureWindow`s gains exactly `DAYLIGHT_ROOM_CAP`; a window on an exterior
wall of an unenclosed area adds nothing; a `glassPartition` between two
enclosed rooms adds its daylight to both; furnishing morale in the same room
still sums on top of the capped daylight.

- [ ] **Step 2: Implement**
- [ ] **Step 3: Verify** — `node test/test-windows.js`, then `npm test`
- [ ] **Step 4: Report** — list changed files; leave them uncommitted

### Task 4: Rendering — opening surround refactor, window pass, night glow

Depends on Task 2. The largest task. Do the refactor first and confirm doors
are untouched before adding anything new.

**Files:**
- Modify: `src/renderer3d/wall-builder.js`
- Modify: `src/renderer3d/world-snapshot.js` — `windows` alongside `doors`
  (`:218`, `:475`)
- Modify: `src/renderer3d/ThreeRenderer.js` — the two `wallBuilder.build(...)`
  call sites (`:3143`, `:3364`), `_updateSnapshot` key lists, the
  `windowsChanged` subscription beside `doorsChanged`, `_updateLightingRamp`
  (`:3532`), and a `renderWindowPreview` beside `renderDoorPreview` (`:2222`)
- Modify: `src/renderer3d/lighting-builder.js` — `glassGlowForDarkness`
- Test: `test/test-windows.js` (extend) — pure-function coverage only

**Part A — extract the surround.** The door pass at `wall-builder.js:332`–`411`
builds side fills and the above-opening band. Pull that into one private
method taking the edge, the opening's width/bottom/top, the wall def and the
material cache, and emitting the fill below (new), beside, and above. The door
pass calls it with bottom `0`; nothing about door output may change.

**Part B — window pass.** Extend `build()` to take `windowData` as a
parameter, add window edges to the set of wall edges skipped by the main wall
loop (same reason doors are skipped: the opening builder rebuilds the
surrounding segments), and include `windowData` in `contentKey` for
`_cacheKey`. Per window: frame (sill, head, two jambs; a 3×2 mullion grid for
`industrialSash`; a heavier frame for the two shielded types) in the type's
`frameTexture` material, a single thin glass box spanning the opening, and the
surround from Part A. Glass: transparent `MeshStandardMaterial`, colour and
opacity from the variant, `roughness` ~0.1, `metalness` ~0.1,
`castShadow = false`, `depthWrite = false`. Honour `wallVisibility ===
'transparent'` and the cutaway path exactly as the door pass does.

**Part C — night glow.** `glassGlowForDarkness(darkness)` in
`lighting-builder.js`, beside the existing three ramp helpers and following
their shape: base 0 by day, rising to a `GLASS_MAX_GLOW` constant at full
darkness. `WallBuilder` exposes the glass materials it created (an array
cleared by `_cleanup`); `ThreeRenderer._updateLightingRamp()` walks it and
sets `emissiveIntensity`. Panes get a warm `emissive` colour set once at
build time; the per-frame write is the scalar only.

**Part D — preview.** `renderWindowPreview(path, windowType)` mirroring
`renderDoorPreview`, for the drag ghost Task 5 calls.

**Interfaces produced:**
- `WallBuilder.build(wallData, doorData, windowData, parentGroup, wallVisibility, cutawayRoom)`
- `WallBuilder.glassMaterials() -> THREE.Material[]`
- `glassGlowForDarkness(darkness) -> number`, `GLASS_MAX_GLOW`
- `ThreeRenderer.renderWindowPreview(path, windowType)`
- snapshot `windows: [{ col, row, edge, type, variant }]`

- [ ] **Step 1: Write the failing tests** — `glassGlowForDarkness` bounds and
  monotonicity (0 at darkness 0, `GLASS_MAX_GLOW` at 1, non-decreasing
  between), in the style of `test/test-light-pools.js`. Geometry itself is not
  unit-testable here (THREE is a browser global); rely on visual check.
- [ ] **Step 2: Implement Part A, verify doors unchanged, then B/C/D**
- [ ] **Step 3: Verify** — `npm test`, then load the running dev server and

- [ ] **Step 4: Report** — list changed files; leave them uncommitted
